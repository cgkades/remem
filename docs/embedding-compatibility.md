# Embedding compatibility and reindex recovery

A model label and vector width do not identify an embedding space. The canonical `remem-space-v1:<sha256>` fingerprint covers schema version, backend, immutable asset revision/content digest, dimensions, pooling, normalization, dtype, and both query/document encoding modes and instruction strings. Property insertion order does not change it. Changing any encoding field creates a different space.

Built-in BGE uses the pinned Hugging Face commit, mean pooling, L2 normalization and q8 weights, plus the loaded Transformers.js and ONNX runtime versions. Offline model directories use a digest of sorted relative file names and file contents, checked before and after loading; symlinks, empty directories or changing assets fail into the explicitly identified hash fallback. Keep offline assets immutable while processes run. The built-in hash algorithm has an immutable versioned asset identity; changes to its algorithm must also change that identity.

`EmbeddingModel.space` describes custom models. Asymmetric models must implement `embedQuery` and `embedDocument` with their declared instructions. Unknown custom identities can provide lexical service, but their vectors never enter similarity comparisons. The semantic catalog recognizer recomputes unidentified/incompatible descriptor vectors from retained text in its own document space rather than trusting label-only vectors. Explicit precomputed write vectors require the matching fingerprint; otherwise ReMem computes its own vector.

Migration 0015 adds nullable fingerprints and staging tables without changing any applied migration. Existing vectors are deliberately unknown: they remain available lexically, but cannot participate in semantic search until rebuilt. New writes stamp their actual resolved space. A neural load fallback stamps the hash space; an inference failure leaves lexical retrieval available and never falsely stamps hash vectors as neural.

Run `remem reembed --batch-size 25` repeatedly after upgrading or switching models. The existing durable claims track each batch. Both memory and catalog vectors are rebuilt from retained titles, summaries, content, aliases and tags, scoped to the runner's provider. Missing vectors are included. Successful results go into staging, while existing active vectors remain unchanged. Source timestamps retain PostgreSQL precision; a changed/deleted source or lost claim cannot promote an obsolete result. Interrupted claims expire after 15 minutes and retry safely; successful stages survive process loss.

`status: completed` describes a batch. **Only `coverage.cutover: completed`, with `compatible === total` and `pending === 0`, describes a complete compatible generation.** Persisting embedding settings records the resolved configured target and proves neither coverage nor cutover. Doctor separately reports fingerprint backlog, staged vectors, active claims and expired interrupted runs.

Cutover promotes complete memory/catalog stages in one transaction after checking full retained-source coverage. A short table lock prevents concurrent writes during this check and promotion (5-second lock timeout, 10-second statement timeout); inference holds no such lock. A failed cutover rolls back both vector surfaces and preserves ready stages. Retry the same command; it reuses those stages rather than re-running inference. Changing targets creates separate fingerprint stages; diagnostics for the configured target do not call another generation compatible. Superseded or foreign-scope records remain excluded from retrieval by the existing authorization filters.

Limitations: storage remains fixed at 384 dimensions. This does not migrate to arbitrary vector widths or add a new mandatory model dependency. Compatible fresh writes can be queried before a historical backlog finishes; full-generation completion remains gated on coverage. Old running processes with a different fingerprint fall back to lexical retrieval after cutover and should be restarted with the intended configuration. Old staging generations may consume disk until their memories are deleted; do not remove a live target's stages during recovery.
