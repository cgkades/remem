# Learning explanations after restart

With a migrated managed PostgreSQL provider, `memory_explain` includes up to five recent project learning entries per provider (at most four providers), alongside the existing transient capture/retrieval explanation. `memory_status` reports availability, bounded recent counts and whether more entries exist. The core `learningHistory` capability can request up to twenty entries; it is provider/project isolated and returns nothing without a project. This reads existing candidate lineage/audit, not candidate or memory bodies.

Each entry includes state, policy/extractor versions and fixed reason codes, proposed confidence when known, resulting memory ID, up to sixteen evidence IDs and which are currently available, and the latest three audit actions. Missing/deleted evidence is marked unavailable rather than reconstructed. Confidence is an extractor annotation, not an independent proof. New numeric snapshots survive explicit forgetting; old entries whose confidence was never retained remain unknown. Replay does not manufacture new claims or approval.

Enabled canonical evidence capture also coalesces content-free gap counters for fixed host/reason categories. Rejected source bodies, credentials, prompts, tool/model output and rejected event identities are never added to these counters. Unknown hosts/reasons map to `other`. Disabled capture does not start this writer. Legacy user-only capture still has its transient explanation; persisted evidence gaps require enabled canonical admission.

Counters are cumulative since the last reset and active for thirty days after the most recent gap. This is not an exact sliding-window event total. A stale counter resets when a new gap arrives; stale rows are pruned on a later successful provider counter write. Recent-history output is bounded, not a claim that earlier learning is absent. Existing body-free lineage/audit retention is unchanged. `doctor` reports database-wide pending/approved lineage totals and active gap-counter totals; host tools disclose only the current project.

Telemetry uses one bounded, coalescing writer, deadlines and cancellation. Database/telemetry failures keep the host usable; failed writes are dropped without retries or raw error logging. A crash before telemetry commits can lose counters, and unavailable stores cannot persist their own outage. This is operational visibility rather than a durable callback outbox. Migration 0016 is additive; applied SQL, source admission and capture defaults are unchanged.

Acceptance: `tests/learning-diagnostics.integration.test.ts` exercises real PostgreSQL restart, all four policy outcomes, confidence/audit preservation, limits/isolation, explicit forget, initial unsafe-source rejection, counter expiry and cancellation rollback. Unit tests exercise coalescing, fixed-code sanitization, telemetry failure, shutdown and host-neutral scope forwarding. Native host/package checks remain required before merge.
